# SFL role matrix

What each role may do on each platform, read out of the permission matrices the services
actually enforce - not a description of them.

## How to read it

**Can do** is the capability list: the actions that make a screen that person's job. The
dashboard gates navigation on these, and the service enforces the same constant on the
endpoint behind it, so an entry you can see is an entry the service will accept.

**Can see** is the read list. Nearly every role holds nearly all of them, which is exactly
why gating the sidebar on reads made every account look identical, and why gating moved to
capabilities. They are listed for completeness; they scope nothing.

A role listed under **Holding nothing on this platform** gets no navigation and no API on
that origin. Its accounts are refused at that service's sign-in page rather than after it,
because listing an account that cannot work reads as an invitation and is not one.

`SFL_ADMIN` and `DTI_ADMIN` hold every permission on every platform. That is stated by the
rows below like any other, not asserted in prose - an earlier draft of this document said
"every permission on this platform" because its generator could not follow a stream filter,
and being unable to read a matrix is not the same as knowing what is in it.

## How this document is kept true

Every `##` section below is generated from the matrices and asserted by a test. Change a
matrix without changing this file and that module's build fails on the diff.

| Section | Generated and owned by |
| --- | --- |
| IFIMP - Facilities & Infrastructure | `services/sfl-facilities-service` &rarr; `RoleMatrixDocumentTest` |
| SSEMP - Safety, Security & Emergency | `services/sfl-safety-security-service` &rarr; `RoleMatrixDocumentTest` |
| FTLMP - Fleet, Transport & Logistics | `services/sfl-fleet-logistics-service` &rarr; `RoleMatrixDocumentTest` |

Three tests rather than one because no single module can see all three matrices: each
service owns its own, deliberately, and there is no shared place they meet. A test that
wanted the whole picture would have to pull three services' business rules into the shared
library, which is the arrangement the matrices exist to avoid.

Regenerate after a deliberate matrix change:

    mvn -f services/pom.xml test -Dtest=RoleMatrixDocumentTest -Dsfl.roleMatrix.write=true

Then read the diff. If it is not the change you meant, the matrix is wrong, not the document.
